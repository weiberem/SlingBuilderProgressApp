## Gmail und Google OAuth

1. **OAuth apps with External user type and publishing status 'Testing' get refresh tokens that expire after 7 days; the only exemption is when the requested scopes are a subset of the basic identity scopes (openid, userinfo.email, userinfo.profile). Any Gmail scope triggers the 7-day expiry.** _(hoch)_  
   Google's OAuth2 doc (section 'Refresh token expiration'): a project with External user type and Testing status is issued refresh tokens expiring in 7 days 'unless the only OAuth scopes requested are a subset of name, email address, and user profile'. The 'Manage App Audience' help page states: 'Authorizations by a test user will expire seven days from the time of consent. If your OAuth client requests an offline access type and receives a refresh token, that token will also expire.' Testing status is also capped at 100 listed test users. A Workspace admin marking the app 'Trusted' can override both limits, but only for that organisation's users (not applicable to a consumer Gmail account). Moving the app to 'In production' removes the 7-day expiry; tokens then only die on revocation, password change (Gmail scopes), 6 months of non-use, or when more than 50 refresh tokens per account per client ID are issued (oldest invalidated).  
   Quellen: <https://developers.google.com/identity/protocols/oauth2>, <https://support.google.com/cloud/answer/15549945?hl=en>, <https://dev.to/ko-hi/googles-oauth-testing-mode-expires-refresh-tokens-in-7-days-publish-the-consent-screen-before-24hm>

2. **Gmail scope classification: https://mail.google.com/, gmail.readonly, gmail.modify, gmail.compose, gmail.metadata (and gmail.insert) are RESTRICTED; gmail.send is SENSITIVE (no CASA needed). An app's tier is determined by its most restrictive scope.** _(hoch)_  
   Google's 'Choose Gmail API scopes' page lists sensitive vs restricted tiers; restricted scopes require restricted-scope verification plus a security assessment if restricted data is stored/transmitted on servers. Secondary sources (Nylas provider guide, Unipile scopes guide, EmailEngine scope reference) agree: gmail.send is the only Gmail scope that can send mail without being restricted; requesting gmail.send + gmail.readonly makes the app Restricted. gmail.labels and gmail.settings.basic are non-restricted (labels = non-sensitive; settings.basic = sensitive) per the same references.  
   Quellen: <https://developers.google.com/workspace/gmail/api/auth/scopes>, <https://developer.nylas.com/docs/provider-guides/google/google-verification-security-assessment-guide/>, <https://www.unipile.com/gmail-api-scopes-guide/>

3. **An External app set to 'In production' but not verified CAN still be authorised for restricted Gmail scopes: users see the 'Google hasn't verified this app' warning (advanced > continue) and the app is limited to 100 new users in total over the project's lifetime; there is no documented time limit on this state, and refresh tokens do not expire after 7 days in production.** _(hoch)_  
   Google 'Unverified apps' help: 'If your app remains unverified, the unverified app screen will be displayed before the consent screen, and your app will be limited to 100 new users until it is verified.' Google FAQ: 'Unverified apps accessing restricted or sensitive scopes have a 100 new-user cap restriction.' The cap applies over the lifetime of the project and cannot be reset (older wording; third-party guides call it 'lifetime, non-resettable'; if exhausted, Google suggests creating a separate Cloud project for verification). Google's 'When is verification not needed' page explicitly exempts personal-use apps: 'if the app is for your personal use (fewer than 100 users), you and your limited number of users can continue using the app without going through verification'; the OAuth 2.0 Policies define personal use as an app 'not shared with anyone else or ... used by fewer than 100 people (all of whom are known personally to you)'. The restricted-scope verification page lists this personal-use case among the exceptions. Caveats: (a) Workspace-managed accounts may be blocked by admin policy for unverified Gmail apps; (b) forum reports of 'This app is blocked' for individual accounts with risk-based protections or Advanced Protection; neither applies to a normal consumer gmail.com account. The API Services User Data Policy still applies to unverified apps.  
   Quellen: <https://support.google.com/cloud/answer/7454865?hl=en>, <https://support.google.com/cloud/answer/13463817?hl=en>, <https://support.google.com/cloud/answer/13464323?hl=en>

4. **Restricted-scope verification requires a CASA (Cloud Application Security Assessment) by an ADA-authorised lab, yearly; developer self-scan reports are no longer accepted. Current levels are AL1 (formerly Tier 2) and AL2 (formerly Tier 3). AL1 costs roughly USD 540-1,200 per year and takes 1-3 weeks; AL2 roughly USD 4,500-5,400. Google's overall restricted-scope review estimate is about 6 weeks.** _(mittel)_  
   Google 'Security Assessment' help: apps are assigned AL1 or AL2 based on risk; the level can increase with user base/data handling; once AL2, stays AL2. Google communicated (2024) that 'We are no longer accepting developer self-scan reports. Developers will need to obtain an assessor verified Letter of Validation (LOV)' (documented in Cyberduck GitHub issue #16192 and Apps Script community thread). Price points from provider comparisons: TAC Security ~USD 540 (older Google-negotiated rate) / USD 675 Basic AL1 (Sept 2026 snapshot) and USD 5,400 AL2; Leviathan USD 800-1,200 AL1. LOV is valid 12 months, so assessment recurs annually. Google FAQ lists restricted-scope verification at ~6 weeks plus the security assessment. The ADA page (appdefensealliance.dev) could not be fetched directly, so exact AL1 scope (lab-validated self-evidence vs lab scan) is from vendor descriptions.  
   Quellen: <https://support.google.com/cloud/answer/13465431?hl=en>, <https://github.com/iterate-ch/cyberduck/issues/16192>, <https://groups.google.com/g/google-apps-script-community/c/XgsHT2Fr7u8>

5. **The 'Internal' user type is only available when the Cloud project belongs to a Google Workspace (or Cloud Identity) organisation; a project created by a consumer @gmail.com account (no organisation) can only choose 'External'.** _(hoch)_  
   Google's consent-screen help describes Internal as limited to users within your Google Workspace organisation and Internal apps skip verification and the 100-user cap ('Your app will not be subject to the unverified app screen or the 100-user cap if it's designated as internal-only'). Odoo documentation (based on the same console) states: 'Personal Gmail Accounts are only allowed to be External User Type' and advises 'No Organization' as project location. Multiple setup guides repeat that Internal requires a Workspace-owned project. Direct fetch of Google's page was blocked; wording is from snippets and secondary docs.  
   Quellen: <https://support.google.com/cloud/answer/10311615?hl=en>, <https://support.google.com/cloud/answer/7454865?hl=en>, <https://www.odoo.com/documentation/saas-17.4/fr/applications/general/users/google.html>

6. **App passwords still work for consumer Gmail in 2026 for IMAP (imap.gmail.com:993) and SMTP (smtp.gmail.com:465 SSL / 587 STARTTLS). They require 2-Step Verification, are unavailable under Advanced Protection, and Google labels them 'not recommended'. The 2024 'Less Secure Apps' shutdown applied to Workspace accounts (password-only logins), not to app passwords on consumer accounts; the consumer LSA toggle was removed in May 2022.** _(mittel)_  
   Google 'Sign in with app passwords' help: a 16-character passcode usable only with 2-Step Verification on; option missing if the account has Advanced Protection (Advanced Protection revokes existing app passwords). Google's Workspace blog: LSA fully disabled 30 Sept 2024 for Workspace; IMAP is integrated with OAuth. Multiple 2026 guides (Nylas CLI, serversmtp, mailertogo, codewords) confirm app passwords remain the only password-based IMAP/SMTP method for personal Gmail and that since Jan 2025 the IMAP toggle is gone (IMAP always on). Sending via smtp.gmail.com with an app password works; personal Gmail cap is 500 messages/recipients per rolling 24h (Google help 'Limits for sending & getting mail'); community reports lower effective limits (~100/day) via SMTP clients for new accounts.  
   Quellen: <https://support.google.com/accounts/answer/185833?hl=en>, <https://support.google.com/accounts/answer/7539956?hl=en>, <https://workspaceupdates.googleblog.com/2023/09/winding-down-google-sync-and-less-secure-apps-support.html>

7. **Gmail IMAP extensions X-GM-THRID (thread id), X-GM-MSGID (message id), X-GM-LABELS (labels) and X-GM-RAW (Gmail search syntax) are documented and usable via FETCH/SEARCH/STORE, so thread matching over IMAP is feasible.** _(hoch)_  
   Google IMAP Extensions page: X-GM-MSGID is a 64-bit unsigned per-message id stable across folders, fetchable and usable in SEARCH/UID SEARCH; it is the decimal form of the hex id shown in the web UI and Gmail API. X-GM-THRID is the 64-bit thread id matching Gmail's web grouping, fetched via FETCH. X-GM-LABELS: 'retrieve the labels for a given message using the X-GM-LABELS attribute with the FETCH command', STORE +X-GM-LABELS (foo) adds a label, and it works in SEARCH/UID SEARCH; labels also appear as IMAP folders (CREATE/RENAME/DELETE). X-GM-RAW: SEARCH extension accepting full Gmail search syntax (e.g. 'has:attachment in:unread'). Note: the Gmail API's threadId is the hex form of X-GM-THRID (per the MSGID statement; the same mapping is used for threads by common libraries) - verify on the live page.  
   Quellen: <https://developers.google.com/workspace/gmail/imap/imap-extensions>, <https://www.limilabs.com/blog/page/32>

8. **Gmail API push: users.watch must be renewed at least every 7 days (Google recommends calling watch once per day); notifications only carry a historyId and the app must call users.history.list from its last stored historyId; history is kept for at least ~1 week and a too-old startHistoryId returns HTTP 404, requiring a full sync.** _(hoch)_  
   Google push guide: re-call watch at least every 7 days or updates stop; watch response includes 'expiration' (epoch ms); Pub/Sub topic must exist and gmail-api-push@system.gserviceaccount.com needs Publisher permission. Google sync guide: 'History records are typically available for at least one week and often longer'; if startHistoryId is out of range the API returns 404 and the client must perform a full sync (then take historyId from messages.get/list or getProfile). Pub/Sub pricing: first 10 GiB per month of Message Delivery Basic throughput per billing account is free, then USD 40/TiB; for a single mailbox the volume is kilobytes, so cost is effectively zero (storage billed separately, first 24h of retained messages free). A Cloud project with billing enabled is still required for Pub/Sub. Alternative for Phase 1: skip push and poll history.list every few minutes (cheap, no Pub/Sub).  
   Quellen: <https://developers.google.com/workspace/gmail/api/guides/push>, <https://developers.google.com/workspace/gmail/api/guides/sync>, <https://cloud.google.com/pubsub/pricing>

9. **To make a sent message join an existing Gmail thread via the API you must (1) set threadId on the Message resource in messages.send, (2) set In-Reply-To and References headers per RFC 2822 (In-Reply-To = parent Message-ID; References = parent References + parent Message-ID), and (3) keep the Subject matching (Re: prefix allowed).** _(hoch)_  
   Google 'Managing Threads' guide lists exactly these three requirements: 'The requested threadId must be specified on the Message or Draft.Message', 'The References and In-Reply-To headers must be set in compliance with the RFC 2822 standard', 'The Subject headers must match'. Every Gmail message resource carries threadId, so store threadId plus Message-ID/References from the parent to reply. For non-API sending (SMTP with app password), only the RFC headers are available; Gmail will still thread by headers/subject, but there is no guaranteed threadId join.  
   Quellen: <https://developers.google.cn/gmail/api/guides/threads?hl=en>, <https://developers.google.com/workspace/gmail/api/guides/sending>, <https://dev.to/devnik/reply-in-thread-using-nestjs-and-gmail-api-47ec>

**Empfehlung:** Phase 1 (one consumer Gmail user, no Workspace): use the Gmail API with OAuth 2.0 on an External OAuth client whose publishing status is set to 'In production' WITHOUT submitting for verification. Rationale: (a) 'Testing' status is unusable because refresh tokens for any Gmail scope expire every 7 days (only openid/email/profile are exempt); (b) once 'In production', refresh tokens persist (revocation, 6 months unused, 50-token cap only); (c) an unverified production app may request restricted scopes (gmail.readonly / gmail.modify) - Remy simply clicks through the 'Google hasn't verified this app' screen once, and Google's own 'When is verification not needed' page exempts personal-use apps with <100 users known to the developer; the 100-new-user lifetime cap is irrelevant for a single user. Request the minimum: gmail.readonly for full read access (+ gmail.send, sensitive, if the app must send; or gmail.modify if labels must be written). Use a dedicated Cloud project, as the 100-user counter is per project and not resettable. For sync, start with polling users.history.list (every 2-5 min) and a stored historyId with 404 => full-resync fallback; add users.watch + Pub/Sub (free tier covers this, but requires a daily watch renewal job and billing enabled on the project) only if near-real-time matters. For replies, store threadId, Message-ID and References per message and send with threadId + In-Reply-To/References + matching Subject.

Build behind a MailProvider interface (listThreads/search, getThread, getMessage(+attachments), sync(sinceCursor), send(reply{threadRef, inReplyTo, references}), watch/renew) with two implementations: GmailApiProvider (default) and ImapSmtpProvider (imap.gmail.com with X-GM-THRID/X-GM-MSGID/X-GM-LABELS/X-GM-RAW for thread matching, smtp.gmail.com with app password for sending). The IMAP/SMTP path is the no-OAuth fallback for a consumer account with 2-Step Verification (no verification, no cap, no Pub/Sub), but it is 'not recommended' by Google, breaks under Advanced Protection, and could be retired; keep it as a fallback, not the primary path. Store the mapping (Gmail API hex id <-> X-GM-MSGID decimal) in the message model so both providers resolve to the same internal thread entity.

Phase 2 (multi-user): a public app with gmail.readonly/modify needs restricted-scope verification plus annual CASA AL1 (~USD 540-1,200/year, 1-3 weeks lab time, ~6 weeks Google review) - budget it, or redesign to avoid restricted scopes (e.g. only gmail.send (sensitive, no CASA) plus user-forwarded/BCC'd mail into the app, or per-user 'bring your own OAuth client/app password'). The provider interface above keeps that decision open.

**Empfehlung:** Minimal design (phase 1, one user, later multi-user):

1. App registration: one Dropbox app, permission type "Full Dropbox" (App-folder apps cannot see shared folders or mount them), scoped app with exactly account_info.read, files.metadata.read, files.content.read, sharing.read, plus sharing.write only if you want the app to mount the Sling folder itself (otherwise the user mounts it once in the Dropbox UI and sharing.write can be omitted). Leave the app in Development status – fine indefinitely below 50 linked users; no production review needed for Remy, and still none for a handful of later builders.

2. Connect flow (server-side web app): authorization-code flow with response_type=code, token_access_type=offline, state (CSRF), and PKCE (S256) – the backend may additionally send the app secret, but PKCE keeps the design identical if a browser-only variant is ever needed. Store refresh_token encrypted per user (dropbox_account_id as key, keep uid/account_id from /users/get_current_account). Keep expires_at from expires_in (typically 14400 s) and refresh with a ~5-minute buffer; treat 401 invalid_access_token as "refresh now", and a failed refresh as "reconnect required" (user revoked the app).

3. Pick the Sling folder: after connect, call /sharing/list_folders and /sharing/list_mountable_folders; show entries whose owner/name matches the Sling share. If path_lower is absent (unmounted invitation), either prompt the user to accept it in Dropbox or call /sharing/mount_folder (sharing.write; watch for insufficient_quota on a free Basic account). Persist shared_folder_id, path_lower, and a human label. Fallback if Sling only sends a link: store the link URL (+ password) and list via /files/list_folder with shared_link={url}; fetch bytes with /sharing/get_shared_link_file; in this mode no cursor/webhook change detection is available, so the worker re-lists and diffs by name+rev+content_hash on a schedule.

4. Change detection (mounted-folder case): initial sync = /files/list_folder(path=path_lower, recursive=true, include_deleted=false) → iterate has_more → store cursor per (user, folder). Afterwards the worker calls /files/list_folder/continue with the stored cursor; on ListFolderContinueError.reset do a full re-list. Trigger the worker (a) from a webhook endpoint (GET challenge echo with text/plain + nosniff; POST: verify X-Dropbox-Signature HMAC-SHA256 with the app secret, enqueue each account id in list_folder.accounts, respond immediately) and (b) from a safety-net cron (e.g. every 6–12 h) because webhooks only say "something changed for this account" and carry no path. Webhooks do fire when Sling (another member) changes the shared folder, provided the folder is mounted in Remy's account. Skip longpoll – it is designed for client-side apps and holds a connection per account.

5. Sync to Google Drive: for each FileMetadata entry whose (id, rev) is new or whose content_hash differs from what is recorded, call /files/get_temporary_link (4 h validity) and let the worker stream the URL straight into a Google Drive resumable upload (100–250 MB fits comfortably; a direct /files/download with Range header is the resume fallback if a transfer breaks). While streaming, compute the Dropbox content hash (4 MiB SHA-256 blocks, SHA-256 over the block digests) and compare with content_hash before marking the revision synced. Record dropbox_file_id, rev, content_hash, size, server_modified, drive_file_id and sync status in your DB; keep old Drive revisions (or Drive's own revision history) so each Sling manual revision is traceable.

6. Rate limits / robustness: single worker per Dropbox account, never run two list_folder calls for the same account concurrently; on 429 read Retry-After (or body retry_after, often 300 s) and sleep that long, else exponential backoff with jitter; retry 503 likewise; cap concurrency at 2–3 downloads overall. Log token refresh failures and webhook signature failures.

Multi-user later: everything above is already keyed by dropbox_account_id; the only shared global state is the app key/secret and the webhook endpoint. Stay in Development status until 50 users are linked, then apply for Production (needs app icon, usage description, branding compliance) within the two-week window.
